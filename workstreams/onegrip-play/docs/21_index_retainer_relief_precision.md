- **결론: 이산화 정밀화로는 목표(web ≥ 1.70 mm)를 달성할 수 없다. 원인이 이산화가 아니다.**

---

## 0. 먼저 — docs/19 예측(1.91)이 빗나간 진짜 원인

docs/19 시뮬레이션은 web 을 측정할 때
**relief 로 새로 생긴 절단면까지의 거리를 포함하지 않았다.**
원본(relief 전) 메시 표면까지의 거리만 썼기 때문에 목 부근 두께를 과대평가했다.

이번에는 `DS = min(원본 표면 거리, relief 절단면 거리)` 로 바로잡았다.
바로잡은 모델의 예측 web = **1.60 mm** 이고, 실제 CAD 측정값 **1.54 mm** 와
복셀 해상도 차이(0.4 vs 0.5 mm) 안에서 일치한다.

> **즉 이산화가 아니라 relief 절삭 자체가 web 을 1.91 → 1.55 로 깎았다.**

### **네 안이 모든 지표에서 완전히 동일하다.**

이유: relief 도구는 반경 3.75 / 길이 23 mm 의 **굵은 볼록 원통**이다.
0.5 mm 간격 복사본들이 서로 압도적으로 겹치므로,
그 합집합이 이미 연속 Minkowski 합과 사실상 같다.
(가는 물체였다면 이산화 오차가 생기지만 이 경우는 아니다)

### D. FeatureScript 연속 sweep 가능 여부

`opSweep` / `opLoft` 로 원통의 정확한 Minkowski 합(= 원통과 평행이동 복사본의 볼록포)을
만들 수는 있으나 **얻는 것이 없다.** 위 표대로 0.5 mm 이산화가 이미 연속과 동일하다.
→ **연속 sweep 구현은 불필요하다.** (§4 우선순위 1·2·3 모두 실익 없음)

### 결정적 사실

> **web 을 지배하는 변수는 sweep 길이다. 반경·X범위·이산화가 아니다.**
>
> - sweep 3.00 → web 1.60
> - sweep 2.50 → web 1.87 (단 body 2분할)
> - **sweep 2.07 → web 2.12, travel 2.42, 단일 body, 제거 65.7 mm³**
>
> **sweep = 3.00 mm 를 유지하는 한, 어떤 반경·X범위·이산화 조합으로도
> 1.69 mm 를 넘지 못한다** (반경 3.70 이 최대이고, 그보다 줄이면 body 가 분할된다).

### 근거

sweep 길이는 "장애물을 인출 방향으로 얼마나 밀어내며 비켜줄 것인가" 이고,
**요구되는 인출량이 곧 d_service = 2.07 mm** 이다.
따라서 **sweep = 2.07 mm 가 수학적으로 필요·충분한 값**이고,
3.00 mm 는 그 위에 얹은 여유였다. 그 여유가 web 을 0.52 mm 깎고 있었다.

sweep 2.07 로도 실제 travel 은 **2.42 mm** 로 요구치를 0.35 mm 넘긴다.
(relief 바깥에서 retainer 가 자연히 갖는 여유 때문)

**승인해 주시면 sweep 파라미터 한 줄만 바꾸고 실물로 재검증하겠다.**
승인 전까지 CAD 는 현재 상태(sweep 3.00, web 1.54)로 둔다.
