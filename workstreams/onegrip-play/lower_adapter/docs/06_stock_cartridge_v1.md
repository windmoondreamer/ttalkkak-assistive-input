스톡 짐벌은 덱을 **관통**해서 주로 아래로 뻗는다. 덱 개구부는 **비구조**다.
하중은 `손 -> OneGrip -> 스톡 Pitch/Roll -> 스톡 Base -> 캐리어 포켓 -> 캐리어 ->
하우징 립 -> 둘레 벽 -> 스커트 다리 -> 지면` 으로 흐른다.

**20도는 하우징 밑면(지면 평면) 절단 한 곳에만 존재한다.**
덱 법선을 그립 +Z 로 두었으므로 `GRIP_AXIS ⟂ DECK` 는 정의상 성립하고,
검증에서 실제 덱 삼각형 법선으로 재확인했다.

```
Z = -149.9565   스톡 Base 밑면
   Base 슬롯 카운터보어  6.0 x 12.7        깊이 3.5   <- 헤드가 여기 앉는다 (0.5mm 리세스)

   Base 관통 슬롯       3.4 x 11.4        깊이 2.9
Z = -143.4565   Base 내부 포켓 바닥 = Spacer 상면
   Spacer 관통                            두께 7.0

   ⌀3.000 원형 블라인드                     깊이 13.000
Z = -123.4565   블라인드 바닥
```

| 항목 | 실측 |
|---|---|
| 나사를 받는 부품 | **C1 → `Roll_holder` (JJD)**, **C2 → `Roll_holder_2` (RKCD)**. 둘 다 FIXED |
| 암나사 형태 | **⌀3.000 원형 블라인드, 깊이 13.000 mm**. 모델에 나사산 없음 → FDM 셀프탭 전제 (**provisional**) |

| 블라인드 잔여 | **7.000 mm** |
| Base 쪽 통과 | **관통 아님 — 슬롯이다.** 3.4 × 11.4 (Y 방향) |

### 채택 나사 규격

캐리어를 끼우면 헤드 지지면이 `CAR_BOT + 카운터보어깊이 = −152.4565` 로 내려간다.

```
필요 길이 범위 = 22.000 .. 29.000 mm      (물림 >= 6.0,  블라인드 여유 >= 0.5)
```

| 길이 | 물림 | 블라인드 여유 | 판정 |
|---|---:|---:|---|
| M3×16 (스톡) | −0.000 | 13.000 | 물림 없음 |
| M3×20 | 4.000 | 9.000 | 물림 부족 |
| **M3×22** | **6.000** | **7.000** | **채택 — 스톡과 완전히 동일** |
| M3×25 | 9.000 | 4.000 | 가능 |
| M3×30 | 14.000 | −1.000 | **바닥 충돌** |

> **`M3×22` (provisional).** 이전 감사에서 후보로 적었던 M3×22 가 실제 스택업으로도
> 최단 표준 길이임이 확인됐다. 다만 근거는 달라졌다 — 캐리어 두께 9.0 + 카운터보어 3.5
> 조합에서 물림·블라인드 여유가 **스톡(6.000 / 7.000)과 소수 3자리까지 같아진다.**
> 가공은 없다. 나사 2개를 **교체**할 뿐이다.

**캐리어 쪽 구멍은 원형이 아니라 Base 와 같은 Y 슬롯(3.4 × 11.4)** 으로 냈다.
Base 슬롯이 Roll_holder 에 대해 Y 로 ±3.5 mm float 하므로, 원형 구멍이면
포켓(= Base 외형 기준)과 나사(= 탭홀 기준)가 서로 싸운다.

## 4. 사전 검증 B — 전장 / 배선

**중요한 발견 3건.**

1. **전장은 CAD 에 있다.** Arduino Pro Micro(`micro board` + `atmega32U4` +
   12핀 헤더 2개) 와 micro USB 가 `Complete` 어셈블리에 포함돼 있다.
   위치: X[−8.74, 9.08] Y[−63.95, −29.50] Z[−152.81, −141.25].
2. **스톡 Base 는 100 × 143 직사각이 아니라 T 자다.**
   - 본체 **100.000 × 100.000** (Y −23.311 … 76.689)
   - 전장 꼬리 **28.000 × 43.000** (X −13.646 … 14.354, Y −66.311 … −23.311)
3. **전장 포켓은 모델링돼 있지 않다.** 전장 표본 3,010점 중 **2,441점(81.1%)이
   Base 솔리드 내부**다. 즉 실제 부품에는 포켓이 있지만 CAD 에는 없다.
   → **보수적으로 꼬리 전체를 비운다.**

밑면 아래로 실제 튀어나오는 것은 다음뿐이다.

| 부품 | 밑면 아래 Y 범위 | 최저 Z | 밑면 아래 |
|---|---|---:|---:|
| `micro board` | −62.375 … −45.851 | −151.210 | 1.254 |
| `micro usb internal` | −62.389 … −58.307 | −151.985 | 2.029 |
| `micro usb shell` | −63.947 … −58.103 | **−152.806** | **2.850** |

### 확정값

```

                        하우징 -Y 벽에 폭 30.6 mm 슬롯을 지면까지 관통시켰다.
```

- 검증: 전장 표본 12,098점 중 캐리어 **0** / 하우징 **0** 침투.

> **provisional:** 커넥터 형상을 새로 만들지 않았고, 스톡 CAD 에 없는 배선 포켓도
> 추정하지 않았다. 꼬리 영역 전체를 비우는 **보수적 서비스 개구**로 처리했다.

### `docs/05` 실현성 목표 대비

| 지표 | 목표 (docs/05) | 실제 CAD | 차이 | 설명 |

**차이가 난 두 항목의 이유:**

1. **덱 아래 돌출 +1.533 mm** — `docs/05` 는 돌출을 **`Base` 만** 기준으로 쟀다.

2. **고정 바닥 → HAND_REF +7.734 mm** — `docs/05` 는 지면을 카트리지 최저점에
   **정확히 붙여** 계산했다(여유 0). 실제로는 USB 플러그를 꽂아야 하므로

`#usb_clearance` 를 0 으로 두면 (2)는 155.02 가 된다. 조정 가능한 변수다.

## 13. 미해결 / 확인 필요

1. **Base 밑면 카운터보어 실물 확인** — CAD 상 헤드가 밑면보다 0.5 mm 안쪽이다.
   실제 출력물에서 같은지 확인해야 M3×22 물림 6.000 이 성립한다.
2. **⌀3.000 블라인드의 실제 체결 방식** — 나사산이 모델링돼 있지 않다.
   셀프탭인지, 실물에 인서트가 있는지 확인 필요.
3. **전장 포켓 미모델링** — 꼬리 전체를 비우는 보수적 처리로 회피했으나,
   실제 배선 다발 굵기 / 커넥터 방향은 실물 확인이 필요하다.
4. **꼬리가 하우징 밖으로 노출된다** — 꼬리 끝(Y −66.311)이 하우징 −Y 면
   (Y −38.311)보다 **28.0 mm 밖**이다. 의도적 선택이다
   (USB 접근 최선 + 인쇄량 최소). 후면 커버는 별도 승인 항목.
5. **`#usb_clearance = 6.0` 은 가정값.** 실제 마이크로 USB 플러그 몸체로 검증 필요.
   0 으로 낮추면 (2) 지표가 155.02 mm 가 된다.
6. **`GET /features` 429** (Retry-After 23,400 s ≈ 6.5 h). 재생성 상태를 직접 못 읽었다.
   간접 확인: 두 피처 POST 응답 `featureStatus = OK`, `/parts` = solid 2 / wire 0,
   `bodydetails` 둘 다 `type = SOLID` (face 65 / 82),
   `massproperties` 부피가 메시 적분값과 일치(87,490 / 271,171 vs 87,492 / 271,171).
7. **립·덱 턱 45도 챔퍼** — 서포트 제거용 v2 항목 (§10).

## 부록 — FeatureScript 교훈 (이번에 추가)

- **`id + "platea"` 와 `id + "plate" + "a"` 는 다른 id 다.** 헬퍼 안에서
  `id + "a"` 로 만든 body 를 호출부에서 찾을 때 반드시 같은 방식으로 결합해야 한다.
- Onshape `tessellatedfaces` 응답 스키마가 **두 가지**다. 구형은 최상위가 body 리스트에
  `vertices: [x,y,z]`, 신형은 `BTExportTessellatedFacesResponse-898` 로 body 가
  `j["bodies"]` 아래에 있고 `vertices: {"x":..,"y":..,"z":..}` 다.
  **최상위 `facetPoints` 는 비어 있으므로 그것만 보면 "빈 응답" 으로 오판한다.**
- 외부 표준부품 문서(나사 등)는 `/m/` `/v/` 경로 모두 빈 tessellation 을 돌려준다.
  → transform 만 쓰고 치수는 규격으로 모델링해야 한다.
- 어셈블리 instance `name` 에는 `" <1>"` 같은 인스턴스 번호가 붙어 있다.
- **`rot_angle(Rb.T @ R)` 로는 FIXED/MOVING 을 분류할 수 없다.** 그 값은 편향이 아니라
  부품 자체 로컬 방향까지 포함한 절대 방향차다 (마그넷이 110도로 나온다).
  프레임 귀속은 어셈블리 구성으로 확정해야 한다.
